# VM 休眠机制研究

> 结论先行：平台按 **coding agent 活跃度**判定 VM 是否休眠（阈值约 11 分钟），
> 而不是终端 WS 流量。60s 一次 agent prompt 可彻底阻止休眠。

## 现象

- 人离开约 11 分钟后 VM 被冻结（快照挂起），外部访问全部 521
- 冻结期间 WS 断开；用户重新打开共享终端页面后 VM 恢复（RESUMED），但**进程全部丢失**（快照恢复不带内存状态，实际上进程丢失说明是恢复镜像+sleepwatch 重建）
- 平台分配的域名（`<port>-<hash>.monkeycode-ai.online`）在休眠时同样不可达

## 排除法

| 假设 | 实验 | 结果 |
|------|------|------|
| 终端 WS 空闲导致回收 | daemon 保持 WS 连接 + ping | ❌ 仍休眠 |
| 终端无输入数据导致回收 | 每 75s 发 Ctrl-C+回车制造 PTY 流量 | ❌ 仍休眠 |
| **agent 无 LLM 调用导致判定空闲** | 定时向 opencode session 发 prompt | ✅ 不再休眠 |

决定性证据：只有**真实触发 LLM 调用**的交互能阻止休眠。平台统计的活跃度信号在
agent→LLM 链路上（可能来自其计费/代理层的调用记录），与浏览器侧无关。

## 阈值测定

| prompt 间隔 | 结果 |
|------------|------|
| 15 min | ❌ 留有空窗，仍被冻结（多次复现） |
| 60 s | ✅ 连续多天零冻结 |

阈值介于两者之间，实测约 11 分钟。60s 留足裕量且日志可观测（每分钟一条 http=200）。

## 成本

- 每次保活 prompt 仅数 token（"echo keepalive"）
- 60s 一次 ≈ 1440 次/天；若在意可在 120s~300s 内调节（仍低于 11min 阈值）
- 15min 不可用

## 冻结后的自愈（保活失效时的兜底）

即使被冻结也不是死局：

1. 用户打开共享终端页面 → 平台恢复 VM
2. daemon 持续重试 WS，密码在会话激活后即生效（所以重试策略不设上限）
3. sleepwatch 在 VM 内检测 RESUMED，自动重拉保活/网关/隧道组件
4. 队列里预置的部署脚本在连接恢复后自动执行

## 附：与"外部 agent"的关系

平台自身的"外部 agent"功能（邀请 AI 远程协助）同样依赖 agent 活跃度——这就是为什么
给 agent 发一条消息就能唤醒 VM。保活脚本本质上是**用 API 调用模拟这一人工动作**。
